The language

Failures & errors

A failure stops the script immediately — unless you catch it. Every kind of failure shares one JSON payload, so handling code is uniform whether the cause was a bad model answer, a blocked tool call or an assert.

The failure payload


{
    "status": "failure",
    "reason": "label must be one of [\"bug\",\"feature\",\"question\",\"docs\"]",
    "command": "assert r.label in LABELS \"label must be one of {LABELS}\"",
    "line": 24,
    "status_code": "assertion_failed"
}
FieldMeaning
statusAlways "failure".
reasonHuman-readable explanation.
commandThe source line, as plain text, where the failure was raised.
line1-based line number.
status_codeMachine-readable category — see below.

Status codes

status_codeRaised when
assertion_failedAn assert condition is falsy.
explicit_failureThe script executes fail '…'.
invalid_formatA fmt='object' response is not valid JSON (object or array).
restriction_violationA tool call is blocked by an active restrict scope.
llm_errorThe backend failed: network, authentication, timeout, model error.
tool_errorA tool failed: missing file, HTTP error, non-zero shell exit code, invalid URL.
runtime_errorOrdinary runtime problems: undefined name, type mismatch, division by zero, index out of range, missing dict key, call depth exceeded.

The set of codes is provisional.

try / except

Handle failures with try and except name. The caught payload is bound to name as a dict. try without except is a syntax error. Any enforce/forbid and restrict scopes opened inside the try block are unwound before the handler runs.


try {
    let response = ?{fmt='object'} 'A joke about programmers'
} except err {
    let response = {'setup': 'none', 'punchline': err.reason}
}
log("{err.status_code} on line {err.line}")
ℹ️
Not everything is catchable

Syntax errors are found before the script starts and are never catchable. Everything raised while running — including runtime errors — is.

A neat consequence: reading an undefined variable is a catchable runtime_error, which the journal example uses to detect a first run.

assert, fail, success

Three special statements control when the program stops.

assert

assert cond ['message'] raises assertion_failed when the condition is falsy. The message is an optional expression and interpolates like any string.


assert 1 == 2 'Abnormal'
assert len(items) > 0 "expected items, got {len(items)}"

fail

fail reason raises explicit_failure. Use it for conditions that are not simple expressions, such as a CI gate.


if high > 0 {
    fail "{high} high severity finding(s)"
}

success

success [result] stops the script successfully. result is printed to stdout — strings raw, everything else as JSON — and returned by the interpreter. Without a value nothing is printed. A script that simply runs to the end also exits with code 0.


success {'counts': counts, 'summary': summary}

Uncaught failures

An uncaught failure prints the payload (pretty-printed JSON) to stdout and exits with code 1. Even then the variable store is saved, so state recorded before the failure survives.


$ spl examples/triage-issues.spl; echo $?
{
    "status": "failure",
    "reason": "could not triage issue 103",
    "command": "fail \"could not triage issue {issue['id']}\"",
    "line": 32,
    "status_code": "explicit_failure"
}
1

Syntax errors are reported on stderr as file:line:col: syntax error: message with exit code 2.

Retry patterns

LLM output is untrusted input. The idiom is: validate deterministically, feed the rejection reason back, ask again, and give up with fail when the budget is spent.


def triage(issue) {
    let problem = ''
    for attempt in range(3) {
        try {
            let r = ?{fmt='object'} '''
Classify this issue. {problem}
Title: {issue['title']}
Reply as JSON: {{"label": one of {LABELS}}}'''
            assert r.label in LABELS "label must be one of {LABELS}"
            return r
        } except err {
            let problem = "Your previous answer was rejected ({err.reason}). Follow the format exactly."
            log("attempt {attempt + 1} failed: {err.reason}")
        }
    }
    fail "could not triage issue {issue['id']}"
}
💡
Why this works

Variance in LLM output can't be removed, but it can be contained: fmt='object' catches malformed JSON, assert catches semantically wrong JSON, and the retry loop turns both into a second chance with better instructions.
