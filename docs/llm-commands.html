The language

LLM commands

Commands are the non-deterministic part of SPL. Each one is an expression that sends a prompt to the model (or runs a tool first) and evaluates to the answer, so you can assign it, test it, or pass it to a function.

CommandPurposeModifiers
?Ask the model a question.len, fmt
thinkAsk the model to deliberate first.level, show
enforce / forbidScoped rules prepended to every call in a block.—
read_file write_file web_fetch web_search shellRun a runtime tool, then let the model process its output.path, content, url, query, command

Operational modifiers

Every command has sensible defaults and the braces are optional: ?'q', think 'q' and read_file 'what to do' all run as they are. A brace list of modifiers directly after the command name overrides its mode:


think{level='high'} 'What is the meaning of life'
  • Names and values are validated by the parser against a fixed schema per command. Unknown modifiers or values are a syntax error, not silently ignored. Each modifier may appear at most once.
  • String values are quoted and lowercase (level='high'); booleans use Python spelling (show=True).

Ask: ?

? is a prefix operator at unary precedence. The operand is the prompt — a postfix expression, so ?'a' + b means (?'a') + b and -?'n' means -(?'n').


let capital = ?'What is the capital of France?'
let response = ?{len='sentence', fmt='object'} 'A joke about programmers'
let firstName = response.setup
ModifierValuesEffect
len'word' 'sentence' 'paragraph' 'long'A hint prepended to the query: “Answer with a single word.”, “Answer in a single sentence.”, “Answer in a single paragraph.”, “Give a long, detailed answer.” A suggestion to the model, not a hard limit.
fmt'text' (default) 'object''object' asks for JSON and the runtime validates and parses it into a dict or list.

Structured output with fmt='object'

The parser accepts a bare JSON object or array, JSON wrapped in a Markdown code fence, or JSON embedded in surrounding prose. Scalars, or anything unparseable, raise a failure with status_code='invalid_format', which you can catch and retry (see retry patterns).


let r = ?{fmt='object'} '''
Classify this issue as JSON: {{"label": "bug"|"feature", "priority": "low"|"high"}}
Title: {title}'''
assert r.label in ['bug', 'feature'] 'unexpected label'
💡
Escaping JSON templates

Inside a prompt, double the braces of a JSON template: {{"a": 1}} produces {"a": 1}. Single braces are interpolation.

Think: think

Tells the model to deliberate about the problem before answering, and lets you choose how hard.


let diagnosis = think{level='low', show=True} 'Why are tests not passing'
ModifierValuesEffect
level'low' 'medium' 'high'Mapped to the Copilot SDK reasoning effort. If the selected model does not support it, a warning is logged and the model default is used.
showTrue False (default)When True, the model's reasoning stream is written to the log (stderr).

A common idiom is a two-stage pipeline — think in prose, then structure the result with a cheap ?{fmt='object'} call. See code-review.

Enforce & forbid

enforce and forbid take a rule and a block. The rule is in force for every LLM call inside the block, including nested blocks and functions called from it. The runtime keeps the active rules on a stack and prepends them to each query.


enforce 'Answer in English' {
    forbid 'mentioning the word cat' {
        let animal = ?{len='word'} 'Name a pet animal'
    }
}
log(animal)    # enforce/forbid blocks share the enclosing scope, so the result is visible here

Both rules above are sent as:

Rules you must follow strictly:
- You MUST: Answer in English
- You MUST NOT: mentioning the word cat
⚠️
Guidance, not enforcement

Constraints are instructions to the model; the runtime cannot verify that the answer obeys them. Use assert for anything that must hold. Hard guarantees about actions come from restrict.

Tool calls

A tool call has the form tool{param=value} 'instructions', and the braces are optional: read_file 'Read notes.txt and summarize it'. In the MVP the tools are a fixed built-in set; user-defined tools and MCP servers are out of scope.

ToolParameters (all optional)PurposeGoverned by
read_filepathRead a filerestrict fs
write_filepath, contentCreate or modify a filerestrict fs
web_fetchurlFetch a URL (http/https)restrict net
web_searchquerySearch the web (DuckDuckGo): title, URL and snippet of the top resultsrestrict net (host html.duckduckgo.com)
shellcommandRun a shell commandrestrict exec

How a tool call runs

Which side calls the tool depends on what the script supplies. When every parameter the tool needs is given (path for read_file, path and content for write_file, url, query, command), the runtime runs it:

1 · RunThe runtime executes the tool with your parameters after checking restrictions.
→
2 · WrapThe output goes into the prompt inside <tool_output> markers, followed by your instructions.
→
3 · AnswerThe model's reply is the value of the expression.

When a needed parameter is missing, the model calls the tool itself from your instructions, and the parameters you did give stay fixed (the model cannot change them). Restrictions apply to its call exactly as to yours.


let readme = read_file{path='./README.md'} 'Return the file content'   # runtime reads the file
let notes = read_file 'Read ./notes.txt and summarize it'              # model reads the file
let log_text = shell{command='git log --oneline -n 40'} 'Summarize these commits'
let page = web_fetch{url='https://example.com'} 'List the headings'
let news = web_search{query='latest Node.js LTS version'} 'Which version is it?'

Parameters path, url, query and command must evaluate to strings. Tool output is truncated at 200,000 characters.

write_file: two modes

With content deterministic

The script supplies the bytes; the runtime writes them; the model only confirms.


write_file{path='./out/a.txt', content=notes} 'Confirm it was written'

Without content LLM writes

The model produces the content and writes the file itself — but the path is pinned by the script.


write_file{path="./out/{code}.md"} '''
Translate ./in.md to {language}
and write it to the file.'''

Tools the model may use

Inside any ?, think or tool call, the model itself may use these same five tools. Every call it makes goes through the same interception and is checked against the active restrict scopes. Any other Copilot permission request is rejected.

How the final prompt is built

Before each call the runtime assembles sections in a fixed order, separated by blank lines:

  1. Rules from active enforce / forbid blocks.
  2. Active restrictions, described in plain language.
  3. For think: “Think carefully about the problem before giving the final answer.”
  4. The len hint.
  5. For fmt='object': an instruction to reply with ONLY valid JSON.
  6. Your prompt.

Run with --log-level debug to see the exact text of every request and response on stderr.
