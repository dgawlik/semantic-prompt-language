Architecture

How the interpreter in lang/src is put together — useful if you want to embed it, add a backend or contribute.

→

→

Execution model

  • Environments. A chain of variable maps. The global map is seeded from the store. Each user-function call creates a child map whose parent is the function's closure, and each bare { } block a child map of the current one; let always writes to the innermost map. All other blocks reuse the current map.
  • Control signals. break, continue and return propagate as values from block execution, not as exceptions; a return that reaches the top level ends the script.
  • Failures. A Failure exception carries a status code and reason; it is stamped with the source line the first time it passes a statement. try restores the constraint stack, restriction stack and call depth before running the handler.
  • success. Implemented as a SuccessSignal that unwinds to the top level.
  • Persistence. The store is loaded before the first statement and saved in a finally block, so state is kept even after a failure. Functions are excluded.
  • Recursion. User-function calls are capped (default depth 200).

Anatomy of an LLM call

  1. Evaluate the prompt (interpolation happens here, deterministically) and, for tools, the parameters.
  2. Pre-run the tool (explicit tool commands only, and only when the script supplied every parameter the tool needs) through ToolHost, which checks the active restrictions first. Otherwise the model calls the tool with the supplied parameters pinned.
  3. Build the request: assembled prompt, model, reasoning effort, a snapshot of the restrictions and a ToolHost for the model's own tool calls.
  4. Call the backend. The Copilot backend opens a session, registers the five tools (overriding built-ins), and exposes configured MCP tools narrowed by the active scopes. Permissions approve only runtime and enabled MCP tools; a restriction_violation aborts the session and is re-raised as a script failure.
  5. Post-process. The answer is trimmed; with fmt='object' it is parsed into a value or raises invalid_format. The effective parameters are logged.

Embedding

The package exports a small programmatic API from dist/index.js:


import { parse, run, Logger, CopilotBackend, MemoryStore } from 'spl-lang';

const logger = new Logger('silent');
const program = parse("let x = ?'hello'\nsuccess x");
const result = await run(program, {
  backend: new CopilotBackend({ logger, cwd: process.cwd(), timeoutMs: 300_000 }),
  logger,
  store: new MemoryStore(),
  cwd: process.cwd(),
});

if (result.status === 'success') console.log(result.value);
else console.error(result.failure);    // { status, reason, command, line, status_code }

Extension points

Custom backend

Implement LlmBackend to target another model provider:


class MyBackend {
  async call(req) {
    // req.prompt is fully assembled; req.restrictions / req.tools must be honoured for tool use
    return { text: '...', effective: { backend: 'mine' } };
  }
  async close() {}
}

Testing scripts

There is no mock backend: scripts that need an LLM are tested directly on GitHub Copilot. tests/live.ts wraps the real CopilotBackend in a recorder, so a test runs against the real service and can still assert on the assembled prompts (backend.calls[i].prompt). Keep assertions about structure, not wording. Live tests are skipped when the runtime is not authenticated (spl login). Tests that must not reach an LLM use the NoLlm backend from tests/helpers.ts, which fails on any call.
