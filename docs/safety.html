Guards & failures

Model output varies, so SPL makes checks explicit: restrict limits actions, assert and schemas check data, failures can be caught, and human hands decisions to a person.

Restrictions#

restrict limits what tools and agents may touch inside its block. Outside any restriction, tools and agents are allowed by default. A blocked action raises restriction_violation.

Clause Allows
restrict './out' or restrict fs './out' Files inside the folder only
restrict net 'api.example.com' Only these hosts (*.example.com matches subdomains)
restrict exec 'npm,git' Only these executables
restrict mcp 'docs/search' Only these MCP servers (docs, docs/*) or tools (docs/search)

Values are a comma-separated string or a list of strings. Combine clauses with commas; nested or repeated clauses of the same kind intersect, so a scope can only narrow.

What is checked:

  • Files: paths are resolved against --cwd, including .. and symbolic links, before checking.
  • Network: every redirect hop is checked. web_search uses html.duckduckgo.com, so list that host to search inside restrict net.
  • Commands: every executable in pipelines and chains, plus path-like arguments, URLs and redirections. Programs with their own I/O (build tools, package managers) are limited by name only; this is not an OS sandbox.
  • MCP: tools outside the scope are hidden from the agent and rejected if requested. MCP servers themselves are trusted and not sandboxed.

Models are told the active restrictions, and the runtime enforces them on every call. ask and think have no tools at all.

Assertions, fail and success#

  • assert condition 'message' raises assertion_failed when the condition is false.
  • fail reason raises explicit_failure.
  • success value ends the document immediately, even from inside a function. return exits a function, or the document at top level.

Failure payload#

Every failure has the same shape. Uncaught failures are printed to stdout and exit with code 1.

status_code Cause
invalid_format Answer is not valid JSON of the requested fmt
validation_failed Answer does not match the schema
assertion_failed An assert was false
explicit_failure fail was executed
restriction_violation An action was blocked by restrict
tool_error Missing file, HTTP failure or nonzero shell exit
llm_error Authentication, timeout, transport or replay mismatch
runtime_error Undefined name, wrong type, invalid modifier and similar bugs

try / except#

The handler gets the failure payload as a dict. Failures do not roll back earlier writes, and syntax errors are reported before anything runs, so they cannot be caught.

Human in the loop#

human 'question' asks a person and returns their answer as a string. In normal CLI runs, the shell prints the question on stderr and reads one line from stdin, preserving whitespace except the line ending. Execution continues immediately without a suspension or repeating completed tool/model calls. Use repeatable --human <answer> flags to supply exact answers in question order and skip prompting. Remaining questions prompt normally, including with --silent; EOF without an answer fails the script.

Blockquote agents use the ask_human tool for the same workflow (@HUMAN). The answer is returned to the same agent session, which may then make new model calls and save it to a shared variable. Runtime actions completed before the question are not repeated, including actions inside invoked functions.

Explicit checkpoint mode#

For noninteractive automation, --checkpoint still saves progress to a journal, prints the question as JSON and exits with code 3. A later --resume invocation supplies the answer and continues without repeating completed tool or model calls. These modes never read stdin and cannot use --human.

The pending question looks like this:

  • Answer with the latest request_id, not the run_id. Each new question gets a new request ID.
  • --answer text and --answer-file file are alternatives; files keep all whitespace.
  • Finished runs print {"status": "success", "run_id": ..., "value": ...} or a failure envelope.
  • Exit codes: 0 success, 1 failure, 2 usage or invalid answer, 3 waiting, 70 journal error.

Resume needs the same workspace, script, runtime, --model/--mcp options and environment. The journal is not a snapshot: files changed in between stay changed. If a run was interrupted mid-action, SPL refuses to guess and asks for manual recovery. Checkpoints cannot be combined with stores or trace/replay. Journals contain prompts and answers, so keep them private.

In CI, treat exit code 3 as "waiting", publish the question to an authorized channel, and resume in the same persistent workspace once an answer arrives.
